# TypeScriptコード品質の教科書

この文書は、TypeScriptでアプリケーションコードを設計・実装・レビュー・改善
するための一般的な品質基準である。特定のフレームワークやリポジトリ構成を
要求せず、個人開発とチーム開発の両方で使える判断材料を提供する。

品質は「バグがないこと」だけではない。利用者の要求を満たし、変更しやすく、
壊れたときに原因を追跡でき、将来の開発者が安全に扱える状態までを含む。
ISO/IEC 25010の品質モデルを参考にしつつ、TypeScriptの型システム、静的解析、
テスト、レビューで確認できる形に具体化する。

既存の [`code-quality-gate.md`](code-quality-gate.md) は、この文書のうち機械的に
判定できる項目をこのリポジトリのマージゲートへ落とし込んだものである。この
文書はゲートの閾値を追加で定めるものではなく、判断の仕方と改善の順序を定める。

## 1. 品質をどう捉えるか

### 1.1 品質の定義

コード品質とは、コードが次の性質をバランスよく持つ状態である。

| 品質特性           | 望ましい状態                                               | 問題のある状態                                                 |
| ------------------ | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 正確性・機能適合性 | 要求、境界条件、失敗時の振る舞いが実装とテストで説明できる | 正常系だけ動き、入力異常や失敗時の仕様が不明である             |
| 可読性             | 意図、前提、データの流れを少ない推測で読める               | 名前が曖昧で、長い関数や深いネストを追わないと意味がわからない |
| 型安全性           | 型が実行時のデータ境界と整合し、危険な値を狭い範囲で扱う   | `any`、無根拠なアサーション、型と実データの乖離が広がっている  |
| 保守性             | 変更箇所と影響範囲を予測でき、局所的に修正できる           | 一つの変更が無関係な機能へ波及し、修正方法が毎回異なる         |
| テスト容易性       | 依存を差し替え、入力と結果を安定して検証できる             | 時刻、乱数、ネットワーク、グローバル状態に直接依存する         |
| 信頼性             | 失敗を適切に検出・伝播・回復し、再現可能なテストがある     | 例外を握りつぶし、部分的な失敗を成功として返す                 |
| 効率性             | 必要な性能・資源量を満たし、測定に基づき最適化されている   | 推測で複雑化するか、明らかな過剰計算・リークを放置する         |
| セキュリティ       | 入力、権限、秘密、外部依存を境界として防御している         | 型検査を入力検証と誤解し、認可や秘密管理を呼び出し側に任せる   |

すべての特性を同じ強さで最大化することはできない。たとえば、性能のために
キャッシュを導入すると一貫性とテスト容易性が下がることがある。レビューでは
「どの品質特性を、どの制約のもとで優先したか」を明示し、トレードオフを隠さない。

### 1.2 品質はコード片でなく変更単位で評価する

品質判断の対象は、一行の美しさではなく、変更が要求・設計・実装・テスト・運用に
与える影響である。レビューでは次を確認する。

1. 変更の目的と、変更しない範囲が説明されている。
2. 主要な成功経路、失敗経路、境界条件が実装されている。
3. 変更後に読み手が保守できる構造になっている。
4. 自動チェックで検出できる欠陥を自動チェックへ委ねている。
5. 人の判断が必要な設計・仕様・リスクがレビューに残っている。

## 2. 可読性と型安全性

### 2.1 可読性の判断基準

可読性は、コードを初めて読む実装者が「何をするか」「なぜそうするか」「失敗時に
どうなるか」を推測せず説明できるかで判断する。

望ましいコードは、ドメイン上の語彙を名前に使い、条件の意味を関数や変数として
表し、正常系と異常系の流れを分ける。短さそのものは目標ではない。圧縮された一行
より、意図を表す数行の方が保守コストを下げることが多い。

レビューでは特に次を見る。

- `data`、`value`、`result` のような文脈を失った名前が残っていないか。
- 真偽値の名前が `is`、`has`、`can` などで意味を伝えているか。
- 条件式の否定、三項演算子の多重化、深いネストが読解を妨げていないか。
- コメントがコードの逐語訳ではなく、仕様や非自明な理由を説明しているか。
- 例外的な処理が正常な処理に埋もれていないか。
- 公開関数の引数、戻り値、エラーの契約が呼び出し側から読めるか。

### 2.2 型安全性の判断基準

TypeScriptの型はコンパイル時の保証であり、JSON、HTTP、環境変数、DB、ユーザー入力
などの実行時データを検証するものではない。外部境界では「受け取った値を検証して
内部の型へ変換する」処理を置く。

次の優先順位を基本とする。

1. 可能なら具体的な interface、union、literal type、ジェネリクスで契約を表す。
2. 不明な入力は `unknown` で受け、型ガードまたはバリデータで絞り込む。
3. `any` は型情報を失う範囲、理由、除去計画をレビューに残した場合だけ使う。
4. `as` と非 null アサーション `!` は、実行時の根拠を隣接コメントまたは構造で示す。
5. `strictNullChecks` などの厳格設定を弱めて局所的なエラーを隠さない。

`unknown` は操作前の絞り込みを要求するが、`any` は存在しないプロパティへのアクセス
まで許して型検査を止める。TypeScript公式ドキュメントでもこの差が説明されている。
型アサーションも実行時検証を追加しないため、外部入力の検証の代用にはならない。

よくある問題と改善例:

```ts
// 問題: 実行時データを型アサーションだけで信頼している
const user = JSON.parse(input) as User;

// 改善: unknownを境界で検証し、検証済みの値だけを内部へ渡す
const parsed: unknown = JSON.parse(input);
const user = parseUser(parsed);
```

型を細かくすることにも限界がある。型が複雑すぎて利用者がアサーションを多用する
なら、型の表現かAPIの責務分割が失敗している。コンパイラを通すことではなく、誤った
状態を表現しにくくすることを目的にする。

## 3. 複雑さ、モジュール、依存関係

### 3.1 関数の複雑さ

一つの関数は一つの判断や変換の責務に集中させる。次の兆候が複数ある場合は分割を
検討する。

- 条件分岐、早期 return、例外処理、ループが混在している。
- 同じ値を何度も変換し、途中状態が多い。
- 引数が多く、引数の組み合わせによって別の関数のように振る舞う。
- ログ、認可、永続化、計算、整形を一つの関数が同時に担当する。
- テストを一つの振る舞いごとに書けない。

サイクロマティック複雑度や認知的複雑度は、危険な箇所を見つける警報である。
数値を下げるためだけに関数を細切れにしたり、条件を間接化したりしてはならない。
分割後に各関数の名前、責務、テストの粒度が明確になることが改善の証拠である。

### 3.2 モジュールの境界

モジュールは、変更理由が近いものをまとめ、変更理由が異なるものを分ける。公開
APIは最小限にし、内部実装を不用意にexportしない。循環依存、巨大な共有ユーティリティ、
何でも受け取るオプションオブジェクトは、境界が曖昧な兆候である。

望ましい依存関係は、依存方向が一方向で、下位の技術詳細が上位の業務ルールを逆に
知らない。モジュールを分ける判断はファイルサイズではなく、独立して理解・変更・
テストできるかで行う。

### 3.3 外部依存と副作用

時刻、乱数、環境変数、ファイル、ネットワーク、DBなどの副作用は、できるだけ境界へ
寄せる。純粋な計算と副作用の調整を分けると、テストが安定し、失敗時の責務も明確になる。
依存性注入は目的ではなく、差し替えが必要な依存を明示するための手段である。

依存パッケージを追加する前に、標準機能・既存依存・小さな自前実装との比較を行う。
追加した依存には、機能上の理由、保守状態、ライセンス、脆弱性、バンドルや起動への
影響を確認する。

## 4. 重複コード

重複は同じ文字列が二度現れることではなく、同じ知識や変更ルールが複数箇所に分散
している状態である。偶然似ている処理まで共通化すると、無関係な変更が結合し、抽象化
の名前が曖昧になる。

共通化を優先する状況:

- 同じ業務ルールを複数箇所で修正する必要がある。
- 同じ入力境界の検証を複数箇所で実施し、一方だけ更新される危険がある。
- 重複箇所が同じ理由で変更される。

重複を残すことが妥当な状況:

- 現時点では似ているだけで、変更理由やライフサイクルが異なる。
- 共通化すると上位層が下位の詳細へ依存する。
- 共通化されたAPIの方が、二つの単純な実装より読みにくい。

重複率や検出件数は探索に使う。数値を下げるために巨大な汎用関数や引数だらけの
ユーティリティを作らず、共通の知識を一箇所に置くことを目的にする。

## 5. テスト容易性と信頼性

### 5.1 テスト容易性

テスト容易性が高いコードは、入力、出力、副作用、失敗を明示できる。テストが難しい
場合は、テストコードの工夫より先に実装の境界を見直す。

- 時刻・乱数・ID生成は注入または固定可能にする。
- ネットワークやDBは境界で差し替え、業務ルールのテストから分離する。
- グローバルな可変状態、テスト間の順序依存、実時間待機を避ける。
- 実装詳細ではなく、利用者に見える振る舞いと不変条件を検証する。
- 失敗を再現できる入力と、失敗が適切に伝播したことを検証する。

### 5.2 信頼性

信頼性は、成功時の処理だけでなく異常時の契約で決まる。次を明確にする。

- どのエラーを呼び出し側へ返すか、どのエラーを回復するか。
- リトライ可能か。リトライするなら回数、遅延、冪等性があるか。
- 部分成功、タイムアウト、キャンセル、重複実行をどう扱うか。
- ログに何を残し、秘密や個人情報を何を残さないか。
- 失敗が利用者、運用者、開発者に適切な形で伝わるか。

`catch` して何もしない、広すぎる例外を成功値へ変換する、失敗をログだけで隠す、
という実装は信頼性を下げる。回復できないエラーは文脈を付けて再送出し、回復できる
エラーは回復した事実と残る制約を明示する。

## 6. パフォーマンスとセキュリティ

### 6.1 パフォーマンス

性能は「速そうなコード」ではなく、代表的な入力と本番に近い条件で測定する。レビュー
では次を確認する。

- ループ内の不要なI/O、N+1アクセス、毎回の全件走査がないか。
- 入力サイズに対する計算量・メモリ量が許容範囲か。
- キャッシュの有効期限、無効化、一貫性、メモリ上限が定義されているか。
- ストリーム、ページング、キャンセル、タイムアウトが必要な処理で考慮されているか。
- 最適化前後を同じ条件で比較できるベンチマークや観測があるか。

性能改善は可読性、正確性、コストとのトレードオフである。測定結果、対象のボトル
ネック、許容する複雑さを記録し、根拠のないマイクロ最適化を避ける。

### 6.2 セキュリティ

TypeScriptの型検査は認証・認可・入力検証・秘密保護を代替しない。Webアプリケーション
ではOWASP Top 10を入口とし、少なくとも次をレビューする。

- 認証済みであることと、対象資源を操作する認可が分けて確認されているか。
- SQL、シェル、HTML、URL、正規表現などの解釈境界へ安全なAPIを使っているか。
- 入力の形式、長さ、許可値、サイズを境界で検証しているか。
- 秘密、トークン、個人情報をソース、ログ、エラーメッセージへ出していないか。
- 依存パッケージ、設定、暗号、CORS、CSRF、SSRF、ファイルパスのリスクを確認したか。
- 重要操作が監査可能で、攻撃や失敗を検知できるログになっているか。

セキュリティ上の不確実性を「型が通る」「テストが通る」で閉じてはならない。リスクの
大きい変更は脅威、権限境界、悪用経路、緩和策をレビューに記録する。

## 7. コードレビューの実用チェックリスト

### 変更全体

- [ ] 目的、非目的、影響範囲が説明されている。
- [ ] 仕様の成功条件と失敗条件がコードまたはテストで確認できる。
- [ ] 変更量と責務が釣り合い、無関係なリファクタリングが混ざっていない。

### 実装

- [ ] 名前、分岐、コメントから意図を追える。
- [ ] 関数・モジュールの責務が一つの変更理由に収まっている。
- [ ] `any`、`as`、`!`、無視されたPromise、空のcatchに根拠がある。
- [ ] 外部入力を検証し、実行時データと型の境界が明確である。
- [ ] 重複の共通化または維持に理由がある。
- [ ] 副作用、エラー、リトライ、キャンセル、タイムアウトが適切である。
- [ ] 性能上のボトルネック、認可、秘密、インジェクションの観点を確認した。

### テストと運用

- [ ] 正常系だけでなく境界条件・失敗・権限不足を検証している。
- [ ] テストは実装詳細ではなく振る舞いを検証し、順序や時間に依存しない。
- [ ] 変更のリスクに応じたログ、メトリクス、ロールバック方針がある。
- [ ] 自動チェックを通過し、人の判断が必要な未解決事項が明示されている。

レビューコメントは好みではなく、具体的なリスク、再現条件、改善案に結びつける。
重大度が低い改善提案は、正しさを妨げない範囲でブロッカーと分ける。レビューの目的は
完璧な一回の変更ではなく、変更後のコードの健全性を上げることである。

## 8. 自動チェックと人の判断の分担

| 自動化に向く項目                           | 人が判断する項目                         |
| ------------------------------------------ | ---------------------------------------- |
| フォーマット、構文、型エラー、lint違反     | 要求を正しく解釈したか                   |
| 未使用コード、循環依存、禁止された依存方向 | APIやモジュール境界が妥当か              |
| テスト失敗、カバレッジ、ミューテーション   | テストケースが重要なリスクを表しているか |
| 既知の秘密、脆弱性、ライセンス違反         | 脅威モデル、認可、情報漏えいの影響       |
| 複雑度、重複率、ファイルサイズの警報       | 複雑さや重複を残すトレードオフ           |
| ベンチマーク、負荷試験、エラー率           | 性能要件、許容コスト、運用上の十分性     |

自動チェックは見逃しを減らし、人は文脈を判断する。自動チェックの合格は品質全体の
証明ではなく、検査した範囲で既知の機械的問題がないという証拠である。逆に、人の
レビューで見つかる問題をlintへ無理に押し込むと、誤検知や形だけの回避が増える。

## 9. メトリクスの使い方

### 9.1 目的

メトリクスは品質そのものではなく、調査対象を選ぶための信号である。目的を先に定める。

- 複雑度: 読み解きにくく、変更時に壊れやすい箇所を探す。
- 重複率: 同じ知識が分散し、修正漏れが起きる箇所を探す。
- カバレッジ: テストされていないコードを探す。
- ミューテーションスコア: テストが実際の誤りを検出できるかを探る。
- 変更失敗率、復旧時間、エラー率: リリース後の信頼性を把握する。
- ビルド時間やレビュー時間: 開発フローの摩擦を把握する。

### 9.2 数値を機械的な合否に使う注意点

- 閾値は普遍的な真理ではなく、コードベース、リスク、測定方法に依存する。
- 全体平均は危険な一ファイルを隠すため、変更コード・重要領域・ファイル単位を使い分ける。
- カバレッジは実行された行の割合であり、アサーションの質、入力の多様性、運用条件を保証しない。
- 複雑度が低くても、間違った抽象化やわかりにくい命名は残りうる。
- 閾値直前のコードを量産するGoodhart効果を避け、数値のための空テストや分割を許さない。
- 測定不能・測定範囲外・ツール失敗をPASSと同一視しない。
- 閾値を変更するときは、目的、対象範囲、誤検知、既存コードへの影響を記録する。

ゲートへ入れるのは、再現性があり、失敗時の行動が明確で、導入コストに見合う項目
だけにする。数値が警報を出したら、最終判断はコード、仕様、実測、リスクで行う。

## 10. 問題を発見した後の改善方針

品質問題は次の順序で扱う。

1. **影響を確認する**: 利用者、データ、セキュリティ、可用性への影響と再現条件を記録する。
2. **変更を止めるか分離する**: 重大な欠陥は先に封じ込め、無関係な改善と混ぜない。
3. **最小の修正を行う**: 仕様を変えずに原因を除き、回帰テストを追加する。
4. **構造を改善する**: 複雑さ、境界、依存、重複を原因に応じて直す。数値だけを下げない。
5. **自動化を追加する**: 同じ問題が繰り返す場合だけ、lint、型、テスト、CIへ検出を移す。
6. **結果を確認する**: テスト、静的解析、必要なら性能・セキュリティ検証を実行する。
7. **知識を更新する**: 再発防止に必要な判断基準だけを文書やADRへ残す。

大きな負債は一度に全て直さず、変更する領域の品質を悪化させないことを優先する。
既存コード全体の改善が必要なら、目的、範囲、完了条件を持つ別の変更として扱う。
品質改善の完了条件は「警告が消えた」ではなく、「原因が減り、正しさをテストでき、
次の変更が安全になった」である。
